> *This was generated by AI during triage.*

## 现象

- 顶部下拉滑到章首时**不会切到上一章**，需改点顶部上三分热区或工具栏「上一章」按钮。
- 切章过程肉眼可感的卡顿（约一帧以上），无过渡动画，章末下滑到下一章的瞬间视觉跳变。

## 复现路径

1. 导入任意两章以上的 TXT/EPUB，进入阅读器。
2. 在 A 章末尾用手机从底部继续下滑（自然 overscroll）—— 不会切章，需改点底部热区才跳到 B 章。
3. 在 B 章顶部继续上滑—— 同上，不会切回 A 章。
4. 实测 iOS 真机 Safari/WKWebView 上切章常有一次 100–300 ms 的可感卡顿。

## 代码路径（已定位）

- `apps/marginal/lib/features/reader/reader_page.dart`
  - L958 `_pageByViewport(int direction)`：章首 `pixels <= 0.5` 触发 `_open(targetRatio: 1.0)` 切上一章；**只响应 `onTapUp` 的三分热区，不接 swipe/overscroll**。
  - L1003–1011 `_prevChapter` / `_nextChapter`：工具栏按钮入口，正常工作。
  - L1145 `ListView.builder(controller: _scrollController, scrollCacheExtent: 1200)`：原生滚动；未挂 `NotificationListener<OverscrollNotification>`、未挂 `ClampingScrollSimulation` 之外的边界手势。
  - L257–355 `_open(...)`：切章前 `await _savePositionNow()`（写 IndexedDB）→ `Future.wait([projection, window.load, fidelity.isAvailable])` → `setState` 全量重建 `paragraphs/chunks/paraKeys/images` → `addPostFrameCallback(jumpTo)`。所有串行 await 都阻塞在 setState 之前。
- `apps/marginal/lib/app/chapter_window.dart` `ChapterWindowSource.load`：含 `paragraphCountBefore` / `_alignStart` / `_alignEnd`，每次切章要扫若干次 repository，长章节 IO 不可忽略。

## 与交互不变量的冲突

- `flutter-reader-interaction-invariants`（memory）明确写了「page-down at chapter end opens the next chapter; page-up at chapter start reopens the previous chapter at its bottom via `_open(targetRatio: 1.0)`」。**当前实现把这条语义只接在了 tap 上，没接 swipe**。
- 这是 mobile-native 验收基线问题（见 [[mobile-first-acceptance-priority]]），与历史上「v1 重建两次都因移动端交互被打回」属同源风险。

## 不变量保护（修时勿踩）

- 三分热区仍是 `onTapUp`，**不要改成 onTap**——onTap 与段落长按的 `GestureDetector` 会双触发/双取消。
- 段落 `GestureDetector` 仍只挂 `onLongPress`，**不要补 onTap**。
- `_open` 内 `addPostFrameCallback(jumpTo)` + `_openGeneration` 守护是必须的：跨章拖动进度条会多次 `_open`，早一版的「per-`onChanged` `_open`」会闪屏/逐章颠簸。
- 自动阅读走 `Ticker` 帧驱动，不要换回 `Timer.periodic`。
- 隐藏 chrome 必须 `IgnorePointer(ignoring: !_chromeVisible)`，**不能新增隐藏时的百分比标签**（`reader-hidden-progress` 已被 d02138a 删除）。
- Stable keys：`reader-scroll-view`、`reader-chrome-toggle-zone`、`reader-top-chrome`、`reader-bottom-chrome` 保持。

## 推荐修复方向（agent 自定细节）

1. **接 swipe/overscroll 跨章**：在 `_buildContent` 的 ListView 上包 `NotificationListener<OverscrollNotification>`，章首 overscroll + 显著速度/位移时 `_open(targetRatio: 1.0)`，章末 overscroll + `_index+1 < _chapters.length` 时 `_open(_index+1)`。阈值参考 `position.viewportDimension * 0.3` + overscroll magnitude > N px；或用 `ClampingScrollPhysics(parent: AlwaysScrollableScrollPhysics())` + 边缘 flingVelocity 触发。
2. **切章卡顿**：
   - `_savePositionNow()` 改为 `unawaited(...)`，不要阻塞 `_open` 的投影/窗口加载（落库失败也不影响阅读体验）。
   - 在 `_onScroll` 接近章末（`pixels >= maxScrollExtent - 1.5 * viewportDimension`）时，预加载下一章 projection + window 的最小可用集，命中时直接替换、不再走 IO。
   - `setState` 重建 `_chunks/_paragraphs/_paraKeys/_images` 的成本：在 `ReaderEpubFidelityView` 之外的语义版里，给 ListView 包 `AnimatedSwitcher` 或 fade transition 200ms，掩盖 100ms 量级的阻塞（即使不可完全消除）。
   - fidelity XHTML 加载移到背景 future：当前 await 在 `_open` 同步链里，长 EPUB 切章会显著拉长；改为切换到 fidelity 时才阻塞。
3. **可观测**：用 Flutter DevTools Performance overlay 或 timeline 包，记下切章 P50/P95 帧时长作为修复前后对比基线。

## 验收要求

- 单测 + 真机/iOS WKWebView：底部 overscroll 切下一章、顶部 overscroll 切上一章都要可命中（保留 tap 三分热区作为另一条路径）。
- 真机切章 P95 帧时长 < 16ms（60fps 下两帧内完成 setState+jumpTo），或至少肉眼不可感。
- 已有 118/118 测试不动；新加 swipe 跨章 + 切章降级路径各 ≥1 测。
- 不允许在沉浸态显示任何百分比徽章。

## 风险

- 加 swipe 跨章后与「三分热区 tap 跨章」并存：tap 仍是秒级响应，swipe 是手势自然过渡，二者无冲突，但需要在 widget 测试里断言两条路径都通向 `_open`。
- overscroll 阈值在 iPad/H5 不同屏宽表现不同：建议阈值基于 `MediaQuery.textScalerOf(context).scale(_fontSize)` 与 `viewportDimension` 的比值定，而非像素绝对值。
